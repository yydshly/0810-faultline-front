# 冷启动资产优先级与分阶段流送

更新时间：2026-08-11
适用入口：桌面 Web `breakthrough-demo` 三档难度及 reduced 变体

## 目标与边界

本轮只优化“玩家多快看到正式首屏、开始后是否重复解码、后续资产以什么顺序进入”。不改模拟、任务节奏、碰撞、模型字节、材质质量或胜负规则。

公开基线（Pages 提交 `5a5d2661a882d7f3e9c6df831b0a48d4681cf95e`）在 00:00 简报期间请求 40 件 GLB，共 25,565,740 bytes（24.381 MiB）。其中旧 critical 阶段先按目录顺序加载 30 件，前四件为 MBT、采矿车、步枪兵和工兵，共 7,784,924 bytes；一次公网冷启动记录的首件正式模型为 5.762 秒，40 件约 30 秒完成。

这组数字是单次公网证据，不是 FPS，也不能写成 p50/p90。

## 当前调度

### 00:00 简报

初始主通道只登记玩家可见开局、两件玩法地表以及可立即建造/生产的正式轮廓：

| 阶段 | 件数 | 字节 | 并发 | 说明 |
|---|---:|---:|---:|---|
| critical | 16 | 18,888,004 | 4 | 侦察车→哨戒塔→重炮塔→中继→主战坦克→经济/基地/步兵/支援车 |
| level | 2 | 63,032 | 3 | 岩石和辉晶矿床 |
| 简报合计 | 18 | 18,951,036 | — | 相比旧 40 件首屏请求减少 25.9% |

新的首个四并发批次为侦察车、哨戒塔、玩家重炮塔和中继站，共 1,838,836 bytes；相比旧首批 7,784,924 bytes 减少 76.4%。队列保留计划给出的稳定优先级，不再重新按全局目录排序。

### 点击开始后

标准难度的根简报已经拥有一个 tick 0、未修改的标准战场。点击“开始新战局 · 标准”时，应用原地关闭简报、解除战术暂停并规范化 URL；不会销毁 Scene、GLB 解码结果、GPU 资源或资产账本。

以下情况仍必须完整重建，防止把旧战局错误当成新战局：

- 从新兵/老兵切换到另一档难度；
- 在进行中的战局选择“重新部署并更改难度”；
- 已经进入胜利或失败状态；
- 非正式突破战评审夹具。

开始后的独立流送通道与首屏通道并行，但保持较低并发：

| 顺序 | 阶段 | 件数 | 字节 | 并发 |
|---:|---|---:|---:|---:|
| 1 | frontline | 10 | 3,860,552 | 2 |
| 2 | rear | 5 | 1,742,664 | 2 |
| 3 | dressing | 8 | 1,560,188 | 1 |

因此敌方前沿轮廓先于敌后基地，所有会影响辨识的模型又先于纯装饰。完整常规路线最终登记 41 件资产；新增的第 41 件是旧启动计划遗漏、但玩家可立即建造的 `FF-CAN-01`。敌方工兵仍按真正的生成/存档需要增量确保，不为当前路线无条件下载。

### 存档恢复与动态确保

恢复晚期存档时，Scene 仍可能已经用 tick 0 新局登记首屏阶段。恢复后的第一次同步会先把“当前已披露实体 + 当前任务波次”放到独立流送通道，再登记 frontline、rear 和 dressing，避免可见的存档实体被装饰阶段挡住。

同页手动载入也会让下一次资产确保进入 priority 通道：尚在 queued 状态的可见存档资产会从普通流送中晋升；已经 inflight 的请求不会被取消或重复下载，而是安全完成。普通阶段会跳过被 priority 接管的标签，避免一个通道把另一个通道的在途任务误判为失败。

运行时资产失败不影响权威模拟；程序模型继续作为安全回退。极慢网络下，玩家若立即关闭简报并快速侦察，仍可能短暂看到回退模型热替换，但前沿阶段现在会在首个模拟 tick 与剩余首屏加载并行，而不是等所有首屏和地表资产结束后才开始。

## 可观测指标

生产 canvas 暴露以下只读数据：

- `assetLoadFirstMs`：第一件正式资产提交时间；
- `assetLoadCriticalRequested`：关键阶段唯一请求数；
- `assetLoadCriticalSettledMs`：关键阶段成功或失败全部收敛的时间；
- `assetLoadCriticalFailed`：关键阶段失败数；
- `assetLoadCriticalReadyMs`：仅在关键阶段失败为 0 时出现；
- 原有 requested / loaded / completed / failed / retries / phase / status。

同时写入 `faultline-front:first-authored-asset`、`faultline-front:asset-critical-settled` 和无失败时的 `faultline-front:asset-critical-ready` Performance Mark。`settled` 不能冒充 `ready`。

## 本地生产候选证据

环境：1280×720、高画质、Vite production preview；Pages 子路径另由部署冒烟验证。

| 检查 | 结果 |
|---|---|
| 00:00 简报 | 18/18 loaded，critical 16，first 627ms，critical ready 1,782ms |
| 标准开始 | URL 写入 fixture/seed，简报关闭；first/critical 时间保持，证明 Scene 未重建 |
| 后续流送 | 41/41 loaded；阶段 `critical,level,frontline,rear,dressing` |
| 自动续战 | 41/41 loaded；阶段含优先 `ensure`，critical 仍在真实完成后才 ready；failed/retries 均为 0 |
| 重部署 | change 模式仍写入 `deploy=1` 并完整重建 |
| 稳定性 | failed 0、retries 0、控制台 warning/error 0 |

本地文件缓存和本机解码远快于 GitHub Pages 冷网，因此 627ms/1,782ms 只用于证明调度与生命周期正确，不能直接与公网 5.762 秒做网络性能结论。

## 后续优化

本轮不改模型内容。只读盘点发现当前 40 件常用 GLB 中，223 个嵌入 KTX2 image 引用只有 75 个唯一字节哈希，理论重复约 9.944 MiB；此外 42 件模型均未使用 `EXT_meshopt_compression`。下一阶段应单独评估共享纹理/阵营图集与 meshopt，先做真实 Pages 冷/热各 5–10 次采样，再决定是否改变资产封装，不能把这类高风险资产迁移混入调度修复。
